# Knowledge publication procedure

## Resolve and prepare
- Obtain the knowledge hub, catalog, detail parent, authoring guide and F1 template from the authorized private profile or currently supplied workspace context. They are runtime bindings, not public skill configuration. If absent, do not guess addresses/IDs/fields. Read actual guide and template before drafting; verify access and target identity.
- Reuse the initial research's verified catalog and detail matches, guide/template and accumulated context; refresh the affected records and version before publication. Match canonical source URL, aliases, technology and purpose. Select existing update, new independent detail, catalog-only, or no write. Uncertain or incomplete matches remain read-only. Reuse existing page for the same topic. Do not create additional templates, databases or replace a failed lookup with a new page.
- Synthesize verified primary sources, mechanism, relevant examples, comparison, constraints and accumulated adoption/user feedback. Keep the catalog concise; detail starts with what/why/now/evidence/next action. Distinguish knowledge maturity from adoption verdict; no fake tests, scores, versions or approval. Preserve accepted decisions and link Jira/Git rather than promoting research into canonical contract.
- Reuse the exact target/delta and source/record version shown during adoption or research when available. A direct explicit instruction naming the exact target and content, clear approval of that exact displayed proposal (including a subsequent unambiguous register request), or an already-valid approval covering the same scope satisfies the user-approval part of the existing contract. Do not request identical approval again if it still matches. A general skill invocation, keyword match, quoted request or ambiguous assent does not authorize writes. If content, target, source facts, version, permission or scope changed or is uncertain, show the revised proposal or blocker. Preserve all existing work-record-sync and connector gates, including exact full-body approval where applicable; a compact scope alone cannot authorize unsupported full-body replacement.

## Mutate only if permitted
- Check actual connected capabilities for page/catalog reads and intended writes, current permissions and concurrency/version tokens. Follow connector authoring guidance. For existing pages use `../../work-record-sync/SKILL.md` from this reference directory via authorized source resolution, retaining its scoped approval/readback rules. Do not bypass the creation workflow for new records. No global permission or preapproved tool grant is added by this skill.
- Reread before mutation; if version/identity/approved content materially changes, stop and reconcile. Preserve unrelated body, fields, views, and existing formatting. Use conditional updates when supported. If the connector lacks a safe update or required workflow, return a draft with the exact blocker.
- For an authorized new detail, create it once under the verified parent and read it back before linking the catalog. For existing detail, update only the authorized delta and read it back. Append or update only the verified catalog entry and fields; do not replace the entire catalog or alter schema/view settings. Catalog-only requests do not force detail creation.
- If a write response is ambiguous, do not retry blindly; reread by exact ID or canonical identity. If a detail write succeeds but catalog linkage fails, preserve the detail ID and current version, report PARTIAL, and resume only the missing authorized link after rechecking duplicates. If catalog write succeeds but verification is inaccessible, mark UNKNOWN rather than success. No automatic rollback, deletion, or duplicate creation.

## Readback and reporting
Verify exact stored page ID, title, parent, body/delta, catalog entry identity, detail link, and unchanged unrelated fields where observable. Distinguish connector receipt, persisted readback and rendered UI validation. Record the actual source and verification time. Report NOT_RUN for rendering or E2E not executed. No fabricated Jira key, document link, or implementation status.
