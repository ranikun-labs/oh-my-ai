# F1 설명 품질 평가

RPL-119의 목적은 구조가 올바른 보고서뿐 아니라, 독자가 별도 설명 요청 없이 목표와 실제 결과를 이해하는 것이다. `evals.json`은 실제 문제 유형에서 파생한 **합성 입력 12개와 기대 행동 24개**를 정의한다. 최초 실패 응답 원문과 실제 실행 증거는 포함하지 않으며, 이 파일의 존재만으로 모델 행동을 검증했다고 보고하지 않는다.

## 같은 입력으로 비교하는 방법

1. 기존/후보 Source의 정확한 Revision과 실제 로딩된 instruction·Skill 경로를 기록한다.
2. 같은 Runtime·모델·추론/속도 설정으로 독립적인 새 세션을 준비한다. 모델 설정의 실효값을 관측할 수 없으면 UNKNOWN으로 기록한다.
3. 각 사례의 `prompt`를 변경하지 않고 제공한다. 목표 중심·제3자 설명을 요구하는 추가 코칭, 정답 힌트, 불필요한 Worker 호출을 넣지 않는다. 일반 질문 사례는 F1을 강제 로드하지 않는다. 쓰기·실행 권한은 부여하지 않는 평가 환경을 사용한다.
4. 같은 사실의 Before/After 응답을 보관하고, 가능하면 평가자에게 어느 버전인지 알리지 않은 상태로 사례별 assertion과 아래 기준을 확인한다. 검사기 구조 PASS를 의미적 품질 PASS로 승격하지 않는다.
5. 9개 대표 출력 유형과 3개 경계 사례를 분리 보고한다. 실제 PR·Markdown·Commit 산출물 각 1건 이상, 기존 Routing/Hook/보고서 검증, Runtime 로딩은 별도의 근거로 남긴다. 미지원 환경·미실행 평가·평가자의 독립성을 명시한다.

## 사람이 읽는 평가 기준

각 해당 항목을 0(불명확), 1(부분 충족), 2(명확)로 평가한다.

- 무엇을 왜 하는지 이해 가능
- 전체 목표와 이번 작업의 관계
- 현재 사용 가능한 기능과 제안/준비 단계의 구분
- 이번에 실제로 변경된 사실
- 남은 문제·미검증·위험
- 필요한 다음 행동·결정
- 기술 정보와 근거 보존

복합 업무의 권장 목표는 12/14 이상, 0점 항목 없음, 기술 정보 보존 2점이다. 짧은 질문이나 비개발 산출물에는 해당 항목만 평가하고 적용한 항목과 분모를 기록한다. 사실 왜곡, 검증 과장, 기술 근거 손실, 승인 경계 변경은 점수와 관계없이 실패다. 이 기준은 설명 품질 검토용이며 정식 F1의 8개 절·14개 필드·5개 Gate를 바꾸지 않는다.

## 비교 예시 (작성자가 만든 설명 예시, 모델 실행 결과 아님)

입력은 사례 3의 합성 사실이다.

- 이해하기 어려운 표현: React UI S1 완료, pack/install PASS, Pilot C NOT_RUN, Merge PENDING.
- 개선 방향: 여러 제품에서 같은 UI를 재사용하기 위한 패키지 Source 후보를 만들고 패키지를 생성·설치할 수 있는지 확인했다. 실제 제품 화면에 적용하는 작업은 아직 실행하지 않았다. 독립 검수와 Source 병합도 남았다. 근거: React UI S1 Source 후보, pack/install PASS, Pilot C NOT_RUN, Independent Review NOT_RUN, Source Merge PENDING.

검증은 실제 모델 출력으로 진행한다. 평가 예시를 실행 결과로 사용하지 않는다. 새 의미 평가 엔진이나 응답마다 별도 Reviewer를 호출하는 방식은 요구하지 않는다.
