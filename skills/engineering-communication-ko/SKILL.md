# 한국어 개발 결과 보고

첫 문장은 사용자가 겪던 문제와 이번에 달라진 점을 말한다. 세부 로그나 파일 목록으로 시작하지 않는다.

## 보고 순서

1. 해결하려던 문제와 사용자에게 생기는 변화
2. 서비스명, 기능명, 현재 사용자 기능
3. 이번에 실제 바뀐 코드·문서·PR과 새 Commit/HEAD
4. 검증 결과와 확인한 근거
5. 아직 되지 않거나 확인하지 않은 것
6. 다음 행동과 필요한 Owner 결정

## 사람에게 전달하는 간결한 F1

사람에게 전달하는 F1은 기본적으로 `결과`, `검증 및 남은 범위`, `다음 행동`, `결정 요청` 네 절로 간결하게 쓴다. 문제·서비스 기능·이번 변경은 결과에, 확인된 검증·미확인 사항과 기존 다섯 Gate 상태는 검증 및 남은 범위에, 목표·첫 행동·담당 Lane·조건은 다음 행동에 둔다. 다섯 Gate 상태는 각각 구분해 짧게 쓰거나, 같은 상태를 담은 접근 가능한 정본 보고서를 참조한다. 결정 요청에는 필요한 Owner 결정의 정확한 범위를 적고, 없으면 `없음`이라고 쓴다. 매번 간결한 응답과 전체 정본 보고서를 함께 붙이지 않는다.

접근 가능한 기존 정본 보고서가 있으면 그 경로를 참조해 세부를 반복하지 않는다. 정본이 없으면 확인된 사실을 네 절의 요약으로 전달할 수 있지만, 요약을 정본 보고서로 표시하지 않는다.

정본 보고서의 계약은 그대로 유지한다: 여덟 절 `## 문제`, `## 사용자에게 달라지는 점`, `## 서비스 기능`, `## 이번 변경`, `## 검증`, `## 아직 안 되는 것`, `## 다음 행동`, `## 근거`, 서비스별 14개 필드, 기존 다섯 Gate 상태다. 간결한 요약만으로 정본 advisory checker `PASS`를 주장하지 않는다. 정본을 만들지 않았거나 검사하지 않았다면 정본 검사 상태를 `NOT_RUN`으로 표시하고, 요약 자체를 검사해 거부된 경우 실제 결과를 숨기거나 `PASS`·`NOT_RUN`으로 바꾸지 않는다. 이 출력 선택은 정본의 필드·Gate 계약이나 검사기 경계를 완화하지 않는다.

## 서비스별 필수 필드

F1 보고서는 한 서비스를 설명한다. 여러 서비스의 변경을 보고할 때는 서비스별 보고서를 각각 작성한다.

서비스 기능 절에는 서비스명, 기능명, 현재 사용자 기능을 각각 명시한다. 현재 사용자 기능은 사용자가 실제로 할 수 있는 일을 문장으로 설명한다. Jira/PR 식별자, URL, SHA 목록만으로 설명을 대신하지 않는다.

필수 필드는 각각 독립된 Markdown 줄에 한 번만 쓴다. 값 문장에 다른 필드명과 콜론이 등장해도 별도 필드로 세지 않는다. 공백, `-`, `*`, 내용 없는 체크박스만으로 필수값을 채우지 않는다.

이번 변경 절에는 실제 변경을 둔다. 검증 절에는 구현 상태, 검증 상태, 문서 상태, 배포 상태를 각각 기록한 뒤 기존 다섯 Gate 상태를 따로 기록한다. 이 네 상태 값은 짧은 근거가 포함된 일반 문구로 쓴다. 기존 Gate 상태 어휘를 다른 상태에 확대하지 않는다.

아직 안 되는 것 절에는 미지원 기능과 미지원 이유를 각각 쓴다. 제한이 없으면 미지원 기능: 없음, 미지원 이유: 해당 없음처럼 명시한다.

다음 행동 절에는 다음 목표, 첫 행동, 담당 Lane, 필요 조건을 각각 둔다. 빈 값은 허용하지 않는다. 이 필드는 실행 책임과 필요한 선행조건을 읽기 쉽게 드러내기 위한 계약이며 실제 작업을 승인하지 않는다.

## 증거 표현

- `Native Test`, `CI`, `Independent Review`, `Runtime E2E`, `Owner Gate`를 각각 별도 상태로 적는다.
- 상태는 `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `UNKNOWN` 중 하나로 쓴다. Owner Gate는 `APPROVED`, `PENDING`, `BLOCKED`, `UNKNOWN`, `NOT_REQUIRED`를 쓴다.
- PASS에는 실행 명령·CI 링크·검수자와 고정 HEAD 등 확인 가능한 근거를 붙인다.
- 요청 모델/Reasoning/Fast와 실제 적용값을 구분한다. 실효 설정을 못 읽으면 `UNKNOWN`으로 남긴다.
- 합성 Fixture, 코드 리뷰, 공식 CI, 실제 Runtime E2E는 서로 대신하지 않는다.
- 계획·Patch Candidate·로컬 수정은 Commit이나 PR 업데이트로 표현하지 않는다.
- Reviewer가 자신의 변경을 검수한 결과를 독립 Review로 표시하지 않는다.
- 개인 정책, 비공개 데이터, Secret을 공개 보고에 넣지 않는다.

## 승인 요청 전 설명

이 보고서에서 사용자 승인을 요청할 때는 질문보다 먼저 다음을 간결하게 설명한다.

- 해결하려는 문제와 제안했거나 이미 만든 변경, 확인한 근거와 검증 범위
- 승인으로 실제 실행될 정확한 행동, 그 행동이 사용자·데이터·운영에 미치는 영향, 이번 승인에서 제외되는 범위
- 추천하는 선택과 이유, 가능한 대안(보류 포함) 및 각 대안의 비용·위험

이미 유효한 승인은 범위·조건·대상을 그대로 보존한다. 같은 승인을 다시 요구하거나 새 행동·대상·영향으로 넓히지 않는다. 추가 승인이 필요한 경우 기존 승인과 새로 필요한 범위를 분리해 설명한다.

승인 요청 전 작성자는 독자 관점에서 승인할 행동·범위·영향·제외를 명확히 다시 말할 수 있는지 셀프체크한다. 실제 오해나 확인·명료화 실패가 드러나면 그 사실과 미해결점을 보존해 보고한다. 이를 감추거나 이미 수락된 결정을 다시 열지 않는다.

## 역할별 실행 요약

F4 결과 보고에서 둘 이상의 역할이 실제 참여했다면 역할별 요약은 필수다. 짧은 요약을 먼저 제시하고, 지원되는 렌더러에서는 `details/summary` 접이식 형식으로 상세 표를 제공한다. 이 형식이 지원되지 않으면 같은 내용을 일반 표로 제공한다.

각 역할별 행에는 실제 역할명과 관측된 Agent 식별자, 실제 작업과 관측된 작업 상태, 역할 배정·재개 횟수, 실행 시도·테스트 실행·검수 이벤트·수정 왕복 횟수를 각각 구분해 근거와 함께 둔다. 배정은 역할이 해당 작업을 맡은 관측 이벤트이고 재개는 같은 역할이 중단 또는 checkpoint 뒤 그 작업을 이어간 관측 이벤트다. 두 횟수는 실행·테스트·검수·수정 왕복 횟수와 별도 계수이며 서로 대신하지 않는다. 요청·실효 Model/Reasoning/Fast와 값 출처, 관측된 시작·종료 시각과 시간 출처, 토큰·비용 근거도 각 행에 둔다. 역할·Agent 식별자나 횟수를 확인할 수 없으면 `UNKNOWN`으로 표시하고 추측하지 않는다. 병렬 역할의 경과 시간은 전체 시간처럼 합산하지 않는다.

각 행의 시간 출처, 공식 사용량 출처, 표시 텍스트 proxy의 포함·제외 범위는 모두 같은 명시적 시작·종료 경계를 가진 실행 구간을 가리켜야 한다. 출처나 proxy 범위가 그 구간을 특정하지 못하거나 서로 다른 구간을 가리키면 값을 함께 비교하지 말고 `비교 불가` 또는 `UNKNOWN`으로 표시한다.

모델·Reasoning·Fast는 위 증거 표현 규칙을 역할별로 적용해 요청값과 직접 확인한 실효값을 나누고, 실효값의 출처를 적는다. 실효 설정을 확인할 자료가 없으면 `UNKNOWN`으로 둔다. 공식 토큰·비용 수치가 있으면 출처를 붙인다. 공식 수치가 없더라도 이미 접근 가능한 표시 텍스트를 잴 수 있을 때만, 추정 범위·계산 방법·포함 및 제외 범위·불확실성을 밝힌 텍스트 proxy를 제공한다. 겹치는 범위는 더하지 않고, 경과 시간이나 가격표로 토큰·비용을 추측하지 않는다. 표시 텍스트와 공식 토큰 자료가 모두 없으면 사용량은 `UNKNOWN`이고, 공식 비용 자료가 없으면 비용은 `UNKNOWN`이다.

새 계측을 만들거나 사용량을 찾기 위해 원문 transcript, raw log, Secret 또는 숨겨진 추론을 탐색하지 않는다. 역할 요약은 참고용 실행 근거이며 기존 F1 다섯 Gate의 상태를 대신하거나 `PASS`로 바꾸지 않는다.

## Advisory 검사기

Markdown 보고서의 필수 절과 상태 표기를 점검하려면 다음을 사용한다:

```bash
OH_MY_AI_ENTRY="$(command -v oh-my-ai || true)"
if [ -n "${OH_MY_AI_HOME:-}" ]; then
  OH_MY_AI_ROOT="$OH_MY_AI_HOME"
elif [ -n "$OH_MY_AI_ENTRY" ]; then
  OH_MY_AI_ROOT="$(node -e 'const fs=require("node:fs"); const path=require("node:path"); process.stdout.write(path.resolve(path.dirname(fs.realpathSync(process.argv[1])), ".."))' "$OH_MY_AI_ENTRY" 2>/dev/null || true)"
else
  OH_MY_AI_ROOT=""
fi

if [ -n "$OH_MY_AI_ROOT" ] && command -v node >/dev/null 2>&1 && [ -f "$OH_MY_AI_ROOT/scripts/f1-report-advisory.mjs" ]; then
  node "$OH_MY_AI_ROOT/scripts/f1-report-advisory.mjs" "$REPORT"
else
  echo "advisory validation NOT_RUN: checker source root or Node runtime unavailable" >&2
fi
```

`oh-my-ai`는 설치된 공개 진입점이며, 이 명령은 실행 중인 서비스 저장소의 현재 디렉터리와 무관하게 그 진입점의 실제 Source root에서 검사기를 실행한다. `$REPORT`는 현재 서비스 저장소의 보고서 경로로 지정한다. Source root를 확인할 수 없거나 Node 실행을 사용할 수 없으면 검사 상태를 `NOT_RUN`으로 기록하고, 확인된 사실로 F1 보고를 계속 작성한다. 이 제한은 F1 보고나 정책 상태를 `PASS`로 만들지 않는다.

검사기는 구조만 확인한다. URL·SHA·테스트·검수 독립성·Owner 승인의 진실성은 검증하지 않는다. 검사기 `PASS`는 독자의 이해도, 추천의 타당성, 유효한 승인 여부를 증명하지 않는다.
